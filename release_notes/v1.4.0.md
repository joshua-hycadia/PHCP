PHCP 1.4.0 - Perl Hydraulic Calculation Program

A Hardy Cross loop-balancing hydraulic solver for fire sprinkler and hydrant systems: a plain-text command language for the model (`.phc`), three windows on that one engine, a calculation report in ASCII text or PDF, an AutoCAD exporter and a pyRevit extension. Australian units by default (L/min, kPa, m, mm).

## Downloads

| file | what it is |
|---|---|
| `phcp_editor.exe` | the text editor: write the model, VALIDATE (F4), CALCULATE (F5), WRITE REPORT (Ctrl+R) |
| `phcp_sheet.exe` | the spreadsheet: the same `.phc` file and the same engine, entered as a sheet |
| `phcp_isometric.exe` | the same calculation, drawn on an isometric grid |
| `phcp.exe` | the command line: `phcp.exe model.phc report.pdf`, `phcp.exe --save model.phc` to keep the results in the model, or `phcp.exe --json model.phc` for another program |

All four are self-contained Windows programs with the pipe and fitting database and the report typeface packed inside. They replace the 1.3.0 files in place.

## What changed since 1.3.0

- **Every calculation is validated.** The final network is checked again from its flows, heads and element equations: numerical (continuity, loop closure, element equations, convergence and settled device states), physical (no pump, check valve, backflow preventer, ratio valve or dry pipe valve passing water backwards, no outlet discharging backwards, no supply taking water in, curves the right way up, plates that fit and meet their duty, every demand reachable from a supply) and design. The result is ACCEPTED, NONCOMPLIANT, REJECTED or INDETERMINATE - on the cover sheet, in new Sections 11 and 14 of the report, in the JSON and in the editor. A converged iteration is no longer, on its own, an accepted calculation.
- **Solver defects corrected.** No device is adjusted on an unconverged solve, and a solve whose device states did not settle is not converged. Reverting a pump check valve that would isolate part of the network left a network out of continuity and called it converged; it now balances and is rejected. An orifice plate's bore is no longer rounded up to its pipe's bore. **No result of a valid model changed:** every example solves to the same flows and pressures as in 1.3.0.
- **Several water supplies** (report Section 12): each supply's operating flow and pressure, its conditional minimum with the others as modelled, its share of the joint demand found in one solve on a stated basis (`OPTION JOINT_BASIS DERATE` or `SCALE`), and supply scenarios - each supply alone, each out of service, and `SCENARIO` lines as requirements.
- **Dry pipe valves** (`DPV`, report Section 13), solved tripped and fully open, with the trip ratio or trip pressure and the accelerator recorded for a later delivery time calculation. No trip or delivery time is calculated or implied.
- **Manufacturers' dry pipe valves in the database** (`DRYVALVE` records, `data/pipes.dat`, dataset of 10 November 2026): Reliable DDX-LP, EX, FX and D; Tyco DPV-1; Viking VXR, F-1 and F-2; Victaulic 768N, 768 and 756 - every size with the loss its data sheet prints (an equivalent length of a stated reference pipe and C, or for Victaulic a flow coefficient Cv), the trip ratio, the rated working pressure and the source document. `DPV P12 100 RATIO 5.5:1 ON VALVE TYCO DPV-1` uses one. The rated pressure is checked, a trip ratio far from the sheet's is flagged, and conflicts found in the data sheets themselves are printed with the valve. Accelerator trip times are not entered.
- **Results saved in the model.** `phcp.exe --save model.phc`, and SAVE in the editor after CALCULATE, write the results into the `.phc` as a block of comment lines at its end, fingerprinted to the model above it. The model reads and solves the same with the block in it; a new solve replaces it. No separate results file.
- **JSON interface 2**: outlet flow is signed; `acceptance`, `validation`, `supplies`, `dry_pipe_valves` and `traceability` added. Exit status 3 is new: REJECTED. The Revit extension reads interface 2.
- New options `SUPPLY_MARGIN`, `SUPPLY_SCENARIOS`, `JOINT_BASIS`. A `VEL_LIMIT` given in a model is now a design requirement.
